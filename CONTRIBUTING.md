# Руководство для контрибьюторов

Привет! Мы рады, что вы хотите внести вклад в развитие
**feeldown-backend**.  
Чтобы поддерживать высокое качество кода и упростить командную работу,
просим придерживаться следующих соглашений.

---

## 1. Соглашение о коммитах

Мы используем
**[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/)**.  
Это
позволяет автоматически генерировать changelog, управлять версиями и
понимать историю изменений.

### Формат сообщения

```
<type>(<scope>): <subject>
```

- **type** – тип изменения (обязательно).
- **scope** – область, которую затрагивает коммит (необязательно, но
  желательно).
- **subject** – краткое описание в **настоящем времени**, без точки в
  конце.

### Допустимые типы

| Тип        | Описание                                                                   |
| ---------- | -------------------------------------------------------------------------- |
| `feat`     | Добавление новой функциональности                                          |
| `fix`      | Исправление ошибки                                                         |
| `docs`     | Изменения в документации                                                   |
| `style`    | Изменения, не влияющие на логику (форматирование, пробелы, запятые и т.п.) |
| `refactor` | Изменение кода, не исправляющее ошибку и не добавляющее функциональность   |
| `perf`     | Улучшение производительности                                               |
| `test`     | Добавление или исправление тестов                                          |
| `chore`    | Обновление зависимостей, настройка сборки, вспомогательные задачи          |
| `ci`       | Изменения в CI/CD конфигурации                                             |
| `build`    | Изменения в системе сборки или внешних зависимостях                        |

### Scope (область)

Рекомендуем указывать название модуля или компонента, например:

- `auth` – аутентификация
- `users` – пользователи
- `posts` – посты
- `notifications` – уведомления
- `friendships` – дружба
- `follow` – подписки
- `block` – блокировки
- `database` – миграции, схемы
- `docker` – изменения в Dockerfile / docker-compose
- `config` – настройки окружения, конфигурационные файлы

### Примеры

```
feat(auth): add Google OAuth2 strategy
fix(users): validate username length on update
docs(readme): update installation instructions
refactor(notifications): use CrudService for read/unread operations
test(posts): add e2e tests for delete endpoint
chore(deps): upgrade prisma to v7.9.0
```

## 2. Кодовое соглашение

### 1. **Наименование**

- Используйте **английский язык** (американский диалект), транслит
  запрещён.
- **Нотации:**
  - `camelCase` – для переменных, функций, полей (например,
    `getUserById`).
  - `UpperCamelCase` – для классов, типов, интерфейсов (например,
    `UserService`).
  - `SCREAMING_SNAKE_CASE` – для констант (например, `DATABASE_URL`).
  - `snake_case` – для полей в БД (Prisma).
- Избегайте **сокращений**, кроме общепринятых (список допустимых
  сокращений есть в соглашении).  
  _Пример:_ `req` → `request`, `res` → `response`, но можно `id`,
  `env`, `config`.
- Название должно **отражать суть**, не содержать артиклей и
  дезинформации.

### 2. **Функции и методы**

- Имя должно содержать **глагол** (например, `get`, `create`,
  `validate`).
- Функция должна **делать одно действие** и быть не длиннее **100
  строк** (оптимально 20–30).
- Принимайте **не более 3 аргументов**.
- Возвращайте ошибку (`throw`) вместо `null` / `undefined`, если это
  логично.
- Не изменяйте переданные параметры.
- Для булевых возвращаемых значений используйте префикс `is` / `has` /
  `validate` (например, `isActive`, `validateUser`).

### 3. **Классы**

- Имена – **существительные** (без глаголов).
- Поля по умолчанию – `private`, инициализируйте их в конструкторе.
- Единый метод-исполнитель: называйте его `execute` (или `run` /
  `init` в зависимости от проекта, но в нашем проекте принят
  `execute`).
- **Запрещено** объявлять методы через лямбда-синтаксис
  (`hello = () => {}`) – используйте обычный метод.

### 4. **Импорты и экспорты**

- Сортируйте импорты в таком порядке:
  1. Типы (интерфейсы, абстрактные классы) – с `import type`.
  2. Данные (функции, классы, переменные).
  3. Вспомогательные файлы (`.json`, `.css`) и импорты-инициализаторы.
- **Не используйте** `import * as ...` и `require`.
- Не совмещайте `export` и `import` в одной строке.

### 5. **Качество кода**

- Извлекайте повторяющийся код в отдельные функции.
- Переименовывайте, если имя перестало отражать суть.
- Удаляйте закомментированный код и лишние комментарии (разрешена
  только документация через JSDoc / Swagger).
- Избегайте «магических чисел/строк» – выносите их в константы.
- **Желательно** не опускать фигурные скобки (кроме случаев, когда
  сразу идёт `return` или `throw`).
- Используйте **пояснительные переменные** для сложных условий.

### 6. **TypeScript**

- Вместо обычного `enum` используйте **`const enum`** – это даёт более
  чистый выходной код и лучшую оптимизацию.

Эти правила уже частично отражены в структуре проекта (например, в
декораторах, сервисах и использовании `CrudService`).  
Придерживайтесь их, чтобы код оставался чистым, читаемым и
единообразным для всей команды.

### Инструменты форматирования и линтинга

- **Prettier** – автоматическое форматирование.  
  Конфиг – `.prettierrc.mjs` (используется общий конфиг
  `@lazy-and-focused/prettier-config`, отключены одинарные кавычки).
- **ESLint** – проверка качества кода.  
  Конфиг – `eslint.config.mjs` (используется `typescript-eslint`,
  правила: `@typescript-eslint/no-require-imports: off`,
  `@typescript-eslint/no-explicit-any: warn`).
- **TypeScript** – строгая типизация.  
  Основной конфиг – `tsconfig.base.json` (target `es2024`, модуль
  `nodenext`, включены декораторы и строгие проверки).

### Стиль именования

| Сущность               | Пример                                         |
| ---------------------- | ---------------------------------------------- |
| Классы / интерфейсы    | `PascalCase` (например, `UserService`)         |
| Функции / переменные   | `camelCase` (например, `getUserById`)          |
| Константы (глобальные) | `UPPER_SNAKE_CASE` (например, `DATABASE_URL`)  |
| Enum-ы                 | `PascalCase` (например, `FriendRequestStatus`) |
| Файлы модулей          | `kebab-case` (например, `user.service.ts`)     |
| Папки                  | `kebab-case` (например, `routes/auth`)         |

### Рекомендации по разработке

1. **Модульность** – каждый модуль инкапсулирует свою логику.
   Контроллер отвечает за маршрутизацию, сервис – за бизнес-логику.
   Используйте `CrudService` для типовых CRUD-операций.
2. **DTO и валидация** – все входные данные должны проходить валидацию
   через `class-validator`. Используйте декораторы `@ApiProperty` для
   Swagger.
3. **Обработка ошибок** – используйте фабрики ошибок из `fockeror`
   (например, `POST_ERRORS`, `AUTH_ERRORS`). Все исключения
   перехватываются глобальными фильтрами.
4. **Документирование API** – каждый эндпоинт должен быть описан с
   помощью `@ApiDocumentation` (см.
   `src/decorators/api-documentation.decorator.ts`).
5. **Тестирование** – пишите unit-тесты для сервисов и e2e-тесты для
   контроллеров. Покрытие критических модулей должно быть не менее
   80%.
6. **Запуск перед коммитом** – убедитесь, что код проходит линтер и
   тесты:

   ```bash
   pnpm run lint
   pnpm run test
   ```

   Для автоматической проверки при коммите рекомендуется настроить
   `husky` и `lint-staged` (см. раздел «Технический долг» в
   `TODO.md`).

## 3. Процесс внесения изменений

1. **Создайте ветку** от `main` (или `main--code-refactoring`),
   назовите её кратко, отражая суть задачи, например:  
   `feature/add-comment-reactions` или `fix/notification-count-bug`.
2. **Вносите изменения** небольшими логическими коммитами с
   осмысленными сообщениями.
3. **Обновите документацию**, если изменения затрагивают API или
   конфигурацию.
4. **Запустите тесты** и убедитесь, что они проходят.
5. **Отправьте Pull Request** в основную ветку, опишите внесённые
   изменения и ссылку на связанную задачу (если есть).
